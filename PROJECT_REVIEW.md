## 4. Сильные стороны

### 4.1 Осознанная архитектура
- **`engine/error_policy.py`** — три уровня ошибок (`RECOVERABLE` / `DEGRADED` / `FATAL`)
  с декоратором `@error_boundary`. Решает реальную проблему, названную прямо в docstring:
  «в pipeline.py ~15 try/except с разной логикой». Это редкость в проектах такого размера.
- **`engine/contracts.py`** — `Protocol`-интерфейсы (`LLMCaller`, `SummaryStore`, …).
  Выбран структурный, а не номинальный подход — обоснование записано в docstring.
- **`check_architecture.py`** — собственный линтер архитектурных границ:
  web-слою запрещено импортировать приватные функции движка. Формализованные правила
  вместо устных договорённостей.
- **Декомпозиция БД**: `db_core` / `db_projects` / `db_chapters` / `db_state` / `db_narrative` /
  `db_settings` вместо одного `db.py`.
- **`mypy.ini`** с явным планом ужесточения по шагам (1→4) и уже включённым
  `disallow_untyped_defs` на трёх модулях.

### 4.2 Качество кода
- SQL везде параметризован. Единственная f-строка (`db_projects.py:81`) подставляет имя таблицы
  из **захардкоженного кортежа** — инъекция невозможна.
- `TODO` / `FIXME` / `HACK` в продуктовом коде: **0**.
- Docstring'и объясняют *почему*, а не *что* — это заметно выше обычного уровня.
- Web-слой разбит на blueprints, а не свален в один `app.py`.
- Секретов в коде нет; `.env` в `.gitignore` и в историю не попадал (в git только `.env.example`).

### 4.3 База знаний
`UNIFIED_ENGINE_MASTER/` с `INDEX.json` (версия 1.8, changelog) — это самостоятельный продукт:
30 жанровых каталогов в JSON, 25 «advanced engines», жанровые чек-листы и контракты,
шаблоны промптов в трёх режимах (QUICK / QUALITY / MASTER). Структура нумерованная и навигируемая.

## 5. Проблемы

### 5.1 Критично: репозиторий засорён артефактами  ✅ *исправлено*

| Что | Сколько | Проблема |
|---|---|---|
| `**/__pycache__/*.pyc` | **48 файлов** | Бинарники в индексе; конфликты при любой смене версии Python |
| `planner/planner.db` | 36 КБ | **Рабочая БД с пользовательскими данными** (1 проект, 2 сцены) в git |
| `planner/planner.db-shm`, `-wal` | 2 файла | Временные файлы SQLite; уже показаны как удалённые в `git status` |

`.gitignore` состоит из **двух строк** (`.env`, `**/.env`). Прямое следствие: `git status`
всегда «грязный» даже сразу после клонирования и запуска, а рабочая БД перезаписывается
при каждом `git checkout`.

**Что делать:**
```bash
git rm -r --cached '**/__pycache__' planner/planner.db planner/planner.db-shm planner/planner.db-wal
```
и расширить `.gitignore`: `__pycache__/`, `*.pyc`, `*.db`, `*.db-shm`, `*.db-wal`,
`.pytest_cache/`, `.mypy_cache/`, `.hypothesis/`.

### 5.2 Тесты: три параллельных набора и падения  ⚠️ *падения исправлены, дублирование осталось*

| Набор | Объём | Статус |
|---|---|---|
| `tests/` (pytest, 42 файла) | 10 189 строк, **834** теста | Не запускается: pytest не установлен в окружении |
| `run_tests.py` (stdlib) | 9 118 строк, **777** тестов | Запускается, **4 падения**, exit 1 |
| `tests_coverage_final.py` + ещё 3 файла в корне | 5 068 строк | Не подключены ни к одному раннеру |

Тестового кода (~23 000 строк) **больше, чем продуктового** (~15 000). Значительная часть —
дублирование одних и тех же проверок в двух-трёх реализациях, которые придётся править синхронно.

**Актуальные падения `run_tests.py`:**
```
✗ pipeline: score_text возвращает dict с total                    AssertionError
✗ pipeline: score_text вычисляет total если отсутствует           AssertionError
✗ pipeline: start_pipeline возвращает run_id                      TypeError: ... unexpected keyword argument 'prefill'
✗ pipeline: start_pipeline авто-ретрай останавливается ...        TypeError: ... unexpected keyword argument 'prefill'
```
Два последних — классическая рассинхронизация: в продуктовый код добавили параметр `prefill`,
а моки в тестах не обновили. Тесты отстали от кода, а раз CI нет — никто не заметил.

**Отдельный баг в самом раннере.** `run_tests.py:5440` вычисляет `total = passed + failed`
*в середине файла*, а печатает его в конце (строка 9108). Поэтому итог выглядит так:

```

```

Отчёт о собственных тестах врёт. Починка — одна строка: считать `total` непосредственно перед печатью.

### 5.4 Нет автоматизации

- **Нет CI** (`.github/` отсутствует). Все три инструмента контроля качества — pytest, mypy,
  `check_architecture.py` — запускаются только вручную и потому не запускаются.
- **Нет `pyproject.toml` / `setup.py`** — проект не устанавливается, только `sys.path.insert`.
- **Нет `LICENSE`** — юридически проект закрыт для любого использования третьими лицами.
- **Нет корневого `README.md`** — репозиторий с тремя подпроектами не имеет точки входа;
  `start_all.sh` не документирован.

### 5.5 Документация разошлась с кодом

`fiction_engine/README.md` описывает структуру так:
```
engine/
├── api.py     — клиенты API
├── db.py      — SQLite
└── state.py   — State Engine
```
Фактически в `engine/` — **40 модулей** (pipeline, cognitive_memory, l3_memory,
narrative_intelligence, continuity_checker, peak_finales, voice_profiles, …).
README отстал примерно на две крупные итерации и сейчас скорее вводит в заблуждение.

Там же зафиксированы конкретные версии моделей в таблице рекомендаций — их придётся
обновлять вручную при каждой смене модельного ряда.

### 5.6 Безопасность

Для локального однопользовательского инструмента модель угроз мягкая, но:

| Находка | Риск |
|---|---|
| `app.run(host="0.0.0.0", port=5000)` без какой-либо аутентификации | Приложение слушает **все интерфейсы**. Кто угодно в той же сети получает полный доступ |
| API-ключи хранятся в SQLite **открытым текстом** (`db_settings.save_api_key`) | Компрометация файла БД = утечка ключей Anthropic / nano-gpt |
| CSRF-защиты нет | Форм и POST-эндпоинтов много, токенов нет |
| `FLASK_SECRET_KEY` по умолчанию случайный при каждом старте | Сессии сбрасываются при перезапуске (в коде честно предупреждено `logging.warning`) |

Смягчает: `debug=False` в проде, ключи не в git.
**Обостряет:** `planner/PROJECT.md` прямо планирует «доступ с телефона через Tailscale» —
то есть выход за пределы localhost уже заложен в замысел. Минимум — `host="127.0.0.1"`
по умолчанию плюс basic-auth перед выставлением наружу.

### 5.7 Подпроект `planner` недоделан

`PROJECT.md` содержит чек-лист «Текущее состояние», где первый же пункт `[ ] DB + миграции`
не отмечен, хотя `engine/migrations.py` и `engine/db.py` написаны. Тестов — **ноль**.
Планируемая интеграция с Fiction Engine (`/export` → localhost:5000) не проверена ничем.

### 8.5 Побочная находка: сломанный эндпоинт

Блок, который переписывался в 8.4, содержал два битых вызова:

```python
summaries = get_l3_summaries(pid)                    # требует before_chapter → TypeError
all_promises.extend(normalize_promises(s["promises"]))  # требует chapter_num → TypeError
```

Оба были обёрнуты в `except Exception: pass`, поэтому **`GET /api/project/context` всегда
возвращал пустой список обещаний** — молча, без единой записи в лог. Это ровно тот
экспорт контекста, которым `planner` собирался пользоваться (`/export` → localhost:5000).

После замены на публичную функцию проверено на временной БД:
```
все главы    : ['Найти убийцу', 'Вернуть долг']   # закрытое обещание отфильтровано
до главы 1   : ['Найти убийцу']
пустой проект: []
```

### 🔴 БАГ 1. Движок UNIFIED_ENGINE_MASTER никогда не попадал в промпты — ✅ исправлено

**Это самая дорогая находка аудита.** В логе пользователя — **70 одинаковых записей**:

                                unsupported operand type(s) for /: 'str' and 'str'

Воспроизводится с первого вызова:

```
build_engine_context("фэнтези", "quick", ...)
  → _build_module_sections → _load_module(module, line_limit)
  → engine_loaders_core.load_module(engine_path="01_tension_curve", module_name=40)
  → engine_path / "03_ADVANCED_ENGINES"      # str / str
  → TypeError
```

**Первопричина** — одна отсутствующая обёртка. В `engine_loaders.py` каждый загрузчик
экспортируется через обёртку, подставляющую путь:

def _load_dialectics_hint():        return _load_dialectics_hint_fn(get_engine_path())

…и только `load_module` ре-экспортировался **напрямую**, без обёртки:

```python
load_module as _load_module,          # ← путь никто не подставляет
```

Поэтому первый же аргумент вызова (`module`) попадал в параметр `engine_path`.

**Последствие.** Исключение ловилось в `_build_engine_block` как `RECOVERABLE` и возвращало `""`.
То есть **весь блок UNIFIED_ENGINE — все 226 файлов базы знаний — молча выпадал из каждого

### 🔴 БАГ 3. Три несовместимых формата State Engine — ✅ исправлено (терпимый парсер, см. §10)

Парсер `db_state._apply_char_field()` ищет ключи полей **в верхнем регистре и
регистрозависимо**:

```python
old_m   = re.search(rf"{regex_key}:\s*(.*)", char_block)          # "СОСТОЯНИЕ:", "ЛОКАЦИЯ:", "ЦЕЛЬ_СЕЙЧАС:"
updated = re.sub(rf"({regex_key}:\s*).*", f"{regex_key}: {new_val}", char_block)
record_fn(f"{char_name}.{field_key.lower()}", old_val, new_val)   # ← вызывается ВСЕГДА
return updated
```

Форматов в проекте оказалось три:

| Источник | Ключи |
|---|---|
| `db_core._default_global()` (что создаёт БД) | `СОСТОЯНИЕ:` `ЛОКАЦИЯ:` `ЦЕЛЬ_СЕЙЧАС:` `ЗНАЕТ:` |
| `UNIFIED_ENGINE_MASTER/08_STATE_ENGINE/global_state_template.md` (что видит автор и LLM) | `Состояние:` `Локация:` `Цель текущая:` `Знает:` |
| Живой проект пользователя «Инженер Хаоса» (8 328 символов) | `Характер:` `Статус:` `Роль:` `Локация:` `Возраст:` … |

Ни один ключ живого проекта не совпадает с тем, что ищет парсер. `re.sub` не заменяет ничего,
блок возвращается неизменным — **но `record_fn` вызывается независимо от факта замены**.
Поэтому `merge_analysis_into_state` возвращает `{"changed": True, "fields": [2 поля]}`,
интерфейс показывает «Применено 2 изменений», а текст State Engine байт в байт прежний.

Воспроизведено на временной БД:

```
changed: True | изменено полей: 2
было : ## ПЕРСОНАЖИ⏎⏎### Марк⏎состояние: спокоен⏎локация: дом⏎
стало: ## ПЕРСОНАЖИ⏎⏎### Марк⏎состояние: спокоен⏎локация: дом⏎
→ State реально изменился: False
```

**Почему не исправил сам:** здесь развилка продуктового решения, а не опечатка.
Два варианта:

1. **Терпимый парсер** — `re.IGNORECASE` + словарь синонимов ключей
   (`ЦЕЛЬ_СЕЙЧАС` ≈ `Цель текущая`), поля, которых нет в блоке, — дописывать.
   Чинит существующие проекты без миграции.
2. **Единый формат** — свести `_default_global()` и `global_state_template.md` к одному
   написанию и мигрировать существующие State.

Независимо от выбора нужна одна безусловная правка: `record_fn` вызывать **только если
`updated != char_block`** — иначе интерфейс продолжит рапортовать о несделанных изменениях.

### 10.1 Баг 3 — терпимый парсер State Engine

Выбран вариант 1: парсер подстраивается под документ, миграция существующих
проектов не нужна.

**Что сделано в `engine/db_state.py`:**

**Синонимы ключей.** Введён словарь `FIELD_ALIASES`, сопоставление регистронезависимое:

| Поле | Понимаемые написания |
|---|---|
| состояние | `СОСТОЯНИЕ` · `Состояние` · `Статус` · `СТАТУС` |
| локация | `ЛОКАЦИЯ` · `Локация` · `Место` · `МЕСТО` |
| цель | `ЦЕЛЬ_СЕЙЧАС` · `Цель текущая` · `Цель сейчас` · `ЦЕЛЬ` · `Цель` |
| знает / не знает | `ЗНАЕТ` · `Знает` · `НЕ_ЗНАЕТ` · `Не знает` |
| момент / статус / следующий шаг | верхний регистр и Title Case |

Синонимы перебираются **по порядку списка**, а не одной альтернативой: если в блоке
есть и `Состояние`, и `Статус`, обновится каноничное `Состояние`, а `Статус` останется нетронутым.

**Заголовки персонажей.** Раньше искался только `### Имя`. Теперь `_find_char_block()`
понимает три формы:

```
### Имя                       — шаблон движка
[ЛУКАШ ВАВРА — ГЛАВНЫЙ ГЕРОЙ]  — формат живого проекта
**Имя**                        — markdown-выделение
```

Это устранило вторую половину бага: раньше персонаж из `[ИМЯ — РОЛЬ]` считался
несуществующим и дописывался **дублем** в чужом формате.

**CRLF.** Отдельная находка, всплывшая при проверке на живых данных: State проекта
«Инженер Хаоса» хранится с `\r\n`. Из-за этого `$` в регекспах не совпадал вообще ни
с чем — то есть даже совпади написание ключа, парсер всё равно бы промахнулся.
Теперь `\r` выделен в отдельную группу шаблона и сохраняется при перезаписи строки,
так что документ не превращается в смесь CRLF и LF.

**Написание сохраняется.** При обновлении поля переиспользуется то написание ключа,
которое уже стоит в документе (`Статус:` остаётся `Статус:`). Отсутствующее поле
дописывается в стиле блока — верхний регистр или Title Case определяется по соседям.

**Больше никаких ложных отчётов.** `record_fn` вызывается только если текст
действительно изменился:

```python
if updated != char_block:
    record_fn(f"{char_name}.{field_key.lower()}", old_val, new_val)
```

Плейсхолдер `[без изменений]`, пустое значение или повтор уже стоящего значения дают
`changed=False` — интерфейс больше не пишет «Применено N изменений» о несделанном.

**Проверка на реальных данных проекта «Инженер Хаоса»:**

```
changed=True  новых персонажей=[]  (дубля нет)
  Лукаш Вавра.состояние: 'Под подпиской о невыезде...' → 'истощён после ритуала'
  Лукаш Вавра.локация:   'Прага, Чехия'                → 'заброшенное депо'
  Лукаш Вавра.знает:     ''                            → 'Матей жив'
  Сюжет.статус:          'завязка'                     → 'кульминация арки 1'
CRLF сохранён: True
```

### 10.2 max_tokens против требуемого объёма главы

**Что было.** Промпты требуют «СТРОГО 2500-3000 слов». Замер на реальной главе
проекта: **6.79 символа на слово**. Кириллица укладывается в ~2.0–2.5 символа на токен.

| Объём | Символов | Токенов @2.0 | @2.5 |
|---|---|---|---|
| 2500 слов | 16 969 | **8 484** | 6 788 |
| 3000 слов | 20 362 | **10 181** | 8 145 |

Настроено было: `generate=8000`, `edit=7000`. То есть потолок стоял **ниже** требования —
модель упиралась в него и обрывала главу на середине фразы. Хуже того, `edit` был
**меньше** `generate`: редактура резала главу, которую генерация успела написать целиком.

**Что сделано:**

1. **Бюджет выводится из целевого объёма**, а не задаётся на глаз
   (`engine/pipeline_config.py`):

   ```python
   TARGET_CHAPTER_WORDS = 3000
   RU_CHARS_PER_WORD    = 6.8    # замер на реальных главах
   RU_CHARS_PER_TOKEN   = 2.0    # консервативно для кириллицы
   PROSE_HEADROOM       = 1.15   # заголовок, разбивка, хвост фразы

   PROSE_MAX_TOKENS = tokens_for_words()   # = 11 730
   ```

   `generate` и `edit` во всех пресетах переведены на общий `PROSE_MAX_TOKENS` —
   редактура больше не может быть теснее генерации. Это ничего не стоит: `max_tokens` —
   потолок, а не предоплата, счёт идёт за реально выданные токены.

2. **Обрыв стал видимым.** Провайдеры сообщают `stop_reason` (Anthropic) и
   `finish_reason` (OpenAI-совместимые), но `call_model` отдаёт строку — менять
   сигнатуру значит трогать весь pipeline и `contracts.LLMCaller`. Причина остановки
   кладётся в `ContextVar` (изолирован по потокам — генерация идёт в фоновых) и
   читается сразу после вызова:

   ```
   stop=max_tokens → «Ответ упёрся в потолок max_tokens — глава оборвана. Написано 2400 слов.»
   stop=length     → то же для OpenAI-совместимых
   stop=end_turn, 1200 слов → «Глава короче требуемого: 1200 слов (промпт требует ~3000).»
   ```

   Порог «короткой главы» был **800 слов при требовании 2500+** — глава, обрезанная
   вдвое, проходила молча. Теперь порог берётся из `MIN_ACCEPTABLE_WORDS = 2000`.

3. **Защита от моделей с меньшим лимитом вывода.** Подъём потолка до 11 730 мог бы
   ломать модели каталога nano-gpt с лимитом 4096/8192. `call_model` один раз
   повторяет вызов с половинным потолком, но **только** если ошибка действительно про
   лимит вывода: лимит запросов, неверный ключ, переполнение окна ввода и сетевые
   сбои пробрасываются как есть — повтор их не лечит, а лишний вызов стоит денег.

4. **Оценка размера промпта.** `len(context_prompt) // 4` — английское отношение,
   занижавшее число токенов примерно в полтора раза, из-за чего защита от переполнения
   окна срабатывала слишком поздно. Заменено на `estimate_tokens()` с отношением 3.0
   символа на токен (компромисс: кириллица ~2.0–2.5, разметка и латиница ~4).
   То же исправлено в `unified_engine` при расчёте бюджета блока движка.

## 12. Обрыв главы связан с продолжением (2026-08-22)

Решение по итогам обсуждения: **потолок токенов не снимать**. Он не оплачивается
(счёт идёт за выданные токены), но остаётся предохранителем от разбега генерации
и живёт внутри окна контекста — а окно нужно самому движку. Текущие 11 730 дают
15–45% запаса над требованием промптов в 2500–3000 слов.

Вместо снятия лимита — правильный механизм для глав длиннее одного вызова:
**распознать обрыв и продолжить с места разрыва**. Продолжение в проекте уже было
(кнопка «✂️ Продолжить» → хвост в 400 слов → режиссёрская заметка → повторный
запуск), но включалось только вручную: автор должен был сам заметить, что глава
оборвана на полуслове.

### 12.1 Флаг вместо строки

`describe_truncation()` возвращал текст — по тексту кнопку не покажешь. Введён
`detect_truncation()` со структурой:

```python
{"truncated": bool, "reason": "max_tokens" | "short" | "", "message": str}
```

- `reason="max_tokens"` — жёсткий обрыв: провайдер сообщил, что упёрся в потолок;
- `reason="short"` — модель закончила сама, но объём заметно ниже требуемого.

`describe_truncation()` оставлен тонкой обёрткой — для мест, где нужна строка.

### 12.2 Путь флага через слои

```
api.py            stop_reason / finish_reason → ContextVar
   ↓
pipeline.detect_truncation()        {truncated, reason, message}
   ↓                        ↓
run_generation           pipeline_steps._flag_truncation()
{truncated, cut_reason,       results["truncated"], ["cut_reason"]
 word_count, warning}         вызывается и в step_generate, и в step_edit
   ↓                        ↓
/generate/status/<job>    /pipeline/start
   ↓                        ↓
generate.html             pipeline.html
#truncation-banner        #cut-banner
```

Проверка обрыва добавлена и в **`step_edit`**: редактура тоже выдаёт полный текст
главы, и её обрыв так же важен — а при авто-повторе именно её результат становится
финальным. Общий помощник `_flag_truncation()` вместо копии кода в двух шагах.

### 12.3 Интерфейс

На обеих страницах генерации появился баннер с одной кнопкой:

| Страница | Баннер | Кнопка |
|---|---|---|
| `generate.html` | `#truncation-banner` над результатом | «✂️ Продолжить главу» → `setContinue(true)` |
| `pipeline.html` | `#cut-banner` рядом с баннером дрейфа голоса | «✂️ Продолжить главу» → `continuePipeline()` |

Формулировка зависит от причины: «✂️ Глава оборвана на полуслове» против
«📏 Глава короче требуемого». Кнопка вызывает **уже существовавшую** логику
сохранения хвоста — новой механики продолжения не добавлялось, подключён только
сигнал. После сохранения хвоста баннер скрывается, страница подводит к кнопке
запуска; при новом запуске баннер сбрасывается.

**Автозапуск сознательно не делался.** Обрыв → автоматический повторный вызов
модели означал бы трату денег без ведома автора, а при неудачном промпте — цикл.
Система распознаёт обрыв и предлагает действие; решение остаётся за автором.

Известное закрыто и проверяется (`tools/scoping.py`, `tools/getcheck.py`,
два класс-теста перебором). Открыты сознательно три дыры, все в этапе 5:

- нет аутентификации при `FE_HOST=0.0.0.0`;
- нет CSRF-токена ни на одном из 55 POST-маршрутов;
- ключи API лежат в SQLite открытым текстом.

Пока этап 5 отложен, цифра не вырастет.

### Что мешает десятке принципиально

Не список задач, а то, что три направления держатся на инструментах, которые
писал и проверял один и тот же человек. Внешние ревью ловили в них ошибку
четыре раза подряд:

1. ложное обоснование в `SAFE_BY_DESIGN` — маршрут вышел из-под проб и реально
   утекал чужую сцену при зелёном наборе;
2. собранное и непроверенное наблюдение в `_proof_ai_assist` — 62/62 зелёные
   при живой утечке;
3. отбор маршрутов по **именам** параметров — `sid` и `job_id` проезжали мимо
   перебора целиком;
4. ложное утверждение в докстринге `getcheck` про исключённый DDL — перенесено
   из чернового grep'а и не перепроверено самим инструментом.

Каждая закрыта, и каждая была найдена **внешним взглядом, а не следующей
проверкой**. Пока это так, потолок ниже десятки — независимо от того, сколько
ещё инструментов добавить.

### Поправка к строке «except → pass» (2026-09-12)

В первой редакции §13 стояло: «19 блоков, из них 4 в `logger.py` — глушитель
в модуле, который существует ради диагностики». Формулировка не выдержала
замера и была несправедливой.

Разбор всех 19 обходом AST: **11 с объяснением в коде, 8 без**. Четыре в
`logger.py` — из объяснённых, и они осмысленны: обработчик логирования не
имеет права бросать исключение, иначе падает приложение, которое он
обслуживает. Это осознанное решение, а не глушитель.

Из восьми «немых» семь — идиома терпимого парсера: `except
json.JSONDecodeError: pass` с переходом к следующей стратегии разбора
(`chapter_analyzer.py` ×2, `pipeline_llm.py` ×3) плюс опциональный импорт
`dotenv` и запасной путь логирования. Ни один не глушит ошибку — все
передают управление дальше.

Настоящим был **один**: `planner/web/blueprints/api_bp.py:246` ловил голый
`Exception` вокруг HTTP-вызова в Fiction Engine и возвращал `sent: false`.
Это форма того самого инцидента, с которого началось внешнее ревью: ошибка
нашего кода — `NameError` на удалённом `_fe_base_url()` — приходила автору
как «FE недоступен», и 55 тестов оставались зелёными, потому что ответ
выглядел штатным. Сужено до `req.exceptions.RequestException`, как строкой
выше на `api_bp.py:185`.

Урок не про `except`, а про метрику: «19 блоков `except → pass`» считает
идиому, а не дефект. Считать надо было объяснённость и ширину перехвата —
тогда из 19 сразу бы выделился один.
